# System Architecture Overview

Figure X presents the overall architecture of the proposed SionnaRT-enabled ns-3 framework. The system follows a layered in-process co-simulation design in which ns-3 remains the primary discrete-event simulator, while Sionna RT is embedded as a geometry-aware radio environment engine. The objective of the architecture is to preserve the mature protocol, traffic, scheduling, and energy-modeling capabilities of ns-3, while enriching the physical channel with deterministic ray-tracing information from Sionna RT.

The upper layer contains the application traffic generators used to create network load. These applications, including video-like, social media, gaming, FTP, and VoIP traffic profiles, interact with the simulator through standard ns-3 abstractions. They are intentionally decoupled from the ray-tracing backend: no application logic is modified when switching between an analytical ns-3 channel and the proposed SionnaRT-based channel. This allows the same end-to-end workload to be evaluated under different propagation assumptions.

The middle layer consists of the ns-3 core and wireless modules, including Wi-Fi 802.11ax, 5G LENA NR, node management, mobility abstractions, and spectrum-channel support. From this layer's perspective, the proposed framework behaves like a native ns-3 extension. Wireless modules continue to request propagation loss, delay, spectrum-channel information, and mobility state through the conventional ns-3 interfaces. The SionnaRT contrib module provides compatible C++ models behind these interfaces, so the higher protocol stack does not need to know whether the underlying channel is analytical or ray-traced.

The SionnaRT wrapper layer is the main integration boundary between ns-3 and the embedded Python environment. It coordinates propagation queries, mobility synchronization, channel-state storage, and data conversion. Rather than allowing each ns-3 model to invoke Sionna RT independently, the wrapper introduces a shared coordination point that manages channel information for all relevant consumers. This makes the architecture coherent across scalar path-loss queries, delay queries, spectrum-channel queries, and phased-array NR channel requests.

A key architectural element is the propagation cache. At a conceptual level, the cache stores recently computed channel information between node pairs and decides whether that information can still be reused. This is necessary because ns-3 may issue a large number of channel queries during packet reception, scheduling, feedback generation, and energy-state transitions, while ray tracing is comparatively expensive. The cache therefore separates the frequency of ns-3 channel requests from the frequency of Sionna RT ray-tracing calls. The detailed cache key, validity rule, invalidation policy, and optimizations are described in the following section.

The lower layer embeds CPython into the ns-3 process through pybind11. This embedded runtime hosts two Python-side services. The first service wraps Sionna RT, loads the radio scene, configures transmitter and receiver arrays, maintains node positions in the ray-tracing scene, and performs batched path-solving operations when requested by the C++ wrapper. The second service supports mobility handling through a Python backend, allowing movement and scene consistency to be managed without leaving the ns-3 process. The C++ wrapper exchanges structured records with these Python services and exposes the resulting information back to ns-3 using native C++ objects.

The overall information flow is as follows. Application traffic and protocol events trigger packet transmissions, scheduling decisions, and channel evaluations inside ns-3. When a wireless module requires channel information, the request is routed to the SionnaRT wrapper. The wrapper first consults the propagation cache. If reusable channel information is available, it is returned immediately to ns-3. Otherwise, the wrapper synchronizes node positions with the embedded Sionna RT scene, invokes a batched ray-tracing calculation, converts the resulting channel records into ns-3-compatible data structures, and updates the cache before answering the original query.

Mobility follows the same principle of separation. ns-3 retains the authoritative event schedule and mobility-model interface, while the embedded backend assists with movement generation, position updates, and scene synchronization. The mobility layer ensures that node positions observed by ns-3 and by Sionna RT remain consistent. The mechanisms used to update positions, handle movement modes, and maintain consistency between the mobility backend and the ray-tracing scene are discussed later.

This architecture has two practical advantages for research evaluation. First, it avoids external inter-process communication between ns-3 and Sionna RT, reducing serialization overhead and simplifying experiment control. Second, it preserves the ns-3 workflow: existing applications, Wi-Fi and NR modules, scheduler logic, trace sources, flow statistics, and energy models remain usable. The framework can therefore be treated as a drop-in geometry-aware channel subsystem rather than a replacement for the simulator.

The results generated by the framework reflect this layered design. The experiment outputs include metadata and traces for propagation behavior, cache activity, Sionna performance, mobility, radio-link adaptation, flow-level performance, MIMO channel gain, CQI feedback, and energy consumption. These measurements allow the impact of ray-traced propagation to be studied across multiple levels of the stack, from physical-channel behavior to application throughput and node energy consumption.

In summary, the proposed architecture separates responsibilities across three domains: ns-3 manages network simulation, the C++ SionnaRT wrapper manages integration and channel-state coordination, and the embedded Python layer provides ray tracing and mobility support.
